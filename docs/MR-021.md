# MR-021 — Snapshots privés incrémentaux et bascule atomique

## Tranche livrée

`mycoradar.snapshots` prépare des snapshots cohérents à partir d'artefacts JSON
déjà calculés hors HTTP. Cette tranche compare les cibles région/espèce/échéance/
couche, conserve celles qui ne changent pas et remplace atomiquement le pointeur
vers un ensemble complet. Elle ne calcule aucun modèle ni score et ne publie
aucun fichier sur le web. **MR-021 reste IN_PROGRESS** pour le raccordement aux
vrais recalculs après admission des données et intégration des PR amont.

Les couches `habitat` et `fruiting` sont des identités distinctes. Les régions,
taxons et versions sont configurés, sans règle spécifique à un pays. Une date
d'échéance doit être une chaîne ISO avec secondes et fuseau explicites ; elle
est normalisée UTC. Une date seule ou un nombre Unix n'est jamais converti
implicitement en échéance précise.

## Lot et incrémentalité

### Plan de calcul — extension du 2 novembre 2026

`Store.recompute(plan_path, calculate, expected=...)` accepte un plan
`recompute-plan-v1` avec une à trente-deux `targets` : les mêmes identités et
versions que le lot ci-dessous, sans `sha256` de résultat ni chemin d'artefact.
Il valide le plan entier et ses budgets avant tout appel au calculateur explicite
fourni par le runner. Une cible déjà présente avec le même modèle et les mêmes
entrées est conservée sans appeler cet adaptateur. Les autres sont calculées
une seule fois par tentative, puis passent par la même validation et bascule
atomique que les lots déjà précalculés.

Le calcul reçoit une copie de ses métadonnées ; une mutation de cette copie
n'altère pas les versions déclarées dans le snapshot. Il retourne des octets
JSON bornés à 1 Mio, sans interprétation scientifique par le store. Tous les
calculs se font **hors verrou de publication et hors requêtes HTTP**. Une
concurrence pendant le calcul donne un conflit à la bascule, sans écraser le
run concurrent. Un échec de calcul, même tardif, n'active aucun résultat ni
n'écrit les sorties antérieures de la tentative dans le store.

Le calculateur peut être rappelé après un échec/conflit : ses effets externes
doivent être idempotents et gérer leur propre admission/quota. Ce contrôleur
ne remplace pas les baux du runner, n'entraîne aucun modèle et n'autorise
aucune publication. Les conditions scientifiques restent inchangées.

Recette : `PYTHONPATH=api/src python scripts/check_snapshot_plan.py` (PowerShell :
définir `$env:PYTHONPATH='api/src'` avant de lancer Python). Un calculateur
inventé est appelé deux fois au premier run, zéro au rejeu puis une fois après
changement du modèle d'une seule cible. 26 tests snapshots et 369 Python
réussissent localement ; 51 PostGIS désélectionnés. Ruff lint/format et mypy
(23 sources) réussis. La CI rejoue ce contrôleur dans l'image API sans réseau.
L'ancienne [CI de staging](evidence/MR-021-staging-ci.json) reste liée à
`89bcea8` ; elle ne valide pas cette extension.

Le lot `snapshot-batch-v1` contient une à trente-deux mises à jour. Chaque mise
à jour déclare `region_id`, `taxon_id`, `valid_at`, `layer`, `model_version`,
une à seize `input_versions` (`source_id`, `sha256`), le chemin local d'un
résultat JSON autonome et son SHA-256. Les chemins résolus restent sous le
répertoire du lot. Les sources répétées et les cibles équivalentes répétées,
y compris avec deux fuseaux décrivant le même instant, sont refusées.

L'identité de cible dépend des quatre dimensions région/taxon/échéance/couche.
Les empreintes de résultat, version de modèle et versions d'entrée déterminent
si cette cible change. Les entrées sont triées pour que leur ordre n'affecte pas
la version ; aucun seuil scientifique n'intervient. Un résultat différent avec
les mêmes versions de modèle et d'entrées est refusé : la non-reproductibilité
ne devient pas une mise à jour silencieuse. Un changement de dépendances avec
résultat identique est tout de même tracé comme une cible changée.

Les cibles absentes du lot sont conservées, sans recalcul ni réécriture. Il
n'existe pas de suppression implicite ou de purge historique. Un snapshot
contient au plus 128 cibles ; lot/descripteur sont limités à 256 Kio, chaque
résultat à 1 Mio. Toute entrée du lot est vérifiée avant la bascule, y compris
la dernière ou une cible inchangée. Une entrée incohérente annule le lot entier.

## Persistance, concurrence et retour arrière

Sous le répertoire opérateur privé :

- `objects/<sha256>.json` : résultats aux octets vérifiés, immuables ;
- `runs/<run_id>.json` : descripteur complet, dont l'empreinte est le `run_id` ;
- `current.json` : seul pointeur actif, remplacé atomiquement après les objets ;
- `.publication-lock.sqlite` : verrou transactionnel entre processus du même hôte.

Les objets sont créés sans écrasement, avec écriture temporaire/fsync et lien
atomique ; un rejeu identique conserve leurs octets et mtime. Le pointeur est
écrit dans un fichier temporaire sur le même volume, puis remplacé par
`os.replace`. Les lecteurs prennent un pointeur complet et vérifient le
descripteur ainsi que tous ses objets. Ils obtiennent un ensemble cohérent ou
un échec explicite, jamais un lot partiel présenté comme sain.

Le publieur exige `expected`, la tête observée par l'appelant ; `None` autorise
uniquement l'initialisation d'un store vide. SQLite sérialise les publieurs avec
une attente bornée à cinq secondes. Un appelant périmé reçoit
`snapshot_head_conflict` et doit relire l'état. Réappliquer le lot sur sa tête
courante ne modifie pas le snapshot ni le mtime du pointeur. Si un acquittement
est perdu après la bascule, réutiliser l'ancienne précondition peut également
donner un conflit sans modifier les résultats : le client doit réconcilier sa
tête, sans forcer une réécriture.

En cas d'échec avant la bascule, la dernière tête saine reste active. Des objets
orphelins complets peuvent subsister ; ils ne sont pas servis par le lecteur
et leur rejeu est sûr. Un retour arrière explicite prend lui aussi une tête
attendue et vérifie intégralement le run demandé. Une cible corrompue ou une
précondition périmée n'est jamais activée. L'ancien historique reste conservé.

Ce contrat couvre la visibilité atomique et les crashes de processus sur un
stockage local d'un seul hôte. Ce n'est pas une garantie de durabilité après
perte matérielle, ni un protocole distribué multi-hôte. Les permissions et la
rétention du répertoire opérateur restent à contrôler ; ne pas supprimer le
verrou pendant que des publieurs tournent. PostGIS reste le stockage métier.

## Garde-fous scientifiques

Les entrées `input_versions` sont des déclarations opérateur ; leurs SHA ne
prouvent pas la provenance, les droits, la géoprécision ou l'antériorité. Le
contrôle de tête détecte une concurrence technique, pas qu'une source est
scientifiquement plus récente qu'une autre. Les protections MR-014/MR-046 et
les futurs calculs admis restent nécessaires avant de brancher un vrai modèle.

Chaque descripteur et chaque réponse CLI garde `publication_allowed=false` et
`scientific_validation=not_performed`. `computed_at`, `data_cutoff` et
`effective_resolution_m` restent nuls au niveau de ce store qui n'interprète pas
scientifiquement les payloads. Le `run_id` n'établit aucune fraîcheur. Aucune
API, couche publique ou promesse de présence n'est ajoutée ; MR-022 traitera
séparément publication quotidienne et cache après admission.

## Recette observée

```powershell
$env:PYTHONPATH='api/src'
uv run --locked python scripts/check_snapshots.py --input data/snapshots/synthetic
```

Le fixture est entièrement inventé : deux régions/taxon fictifs, résultats
indisponibles et scores nuls, aucune observation réelle. Le smoke lance deux
processus CLI sur la même tête vide : un seul gagne. Il rejoue le lot à
l'identique, modifie une dépendance d'une cible en conservant l'autre, puis
restaure le snapshot initial. Tous les fichiers générés sont temporaires et
les entrées restent en lecture seule. La CI rejoue ce script dans l'image API
construite avec réseau désactivé ; le Dockerfile n'a pas besoin de modification.

17 tests ciblés et 360 tests Python locaux réussissent ; 51 PostGIS sont
désélectionnés. Ruff lint/format et mypy (22 sources) réussissent après correction
d'une annotation du helper de smoke et d'une variable/import inutilisés.
`git diff --check` réussi. Docker Desktop n'est pas disponible localement ; le
build/smoke et PostGIS/navigateur sont confiés à la CI du nouveau commit.
Le reçu local consigne les versions et empreintes, sans preuve scientifique.

`artifact_io.py` est le même petit utilitaire standard que dans la PR MR-020,
inclus ici pour une revue et une CI autonomes ; aucun code de runner ou de file
n'est intégré dans cette PR. Les octets communs sont comparés lors de la recette.

Retour arrière : retirer module, smoke, fixture et étape CI, puis reconstruire
l'API. Conserver les fichiers opérateur tant que leurs runs sont nécessaires.
Aucune migration PostGIS, fusion, mise en production ou dépense cloud.

# MR-022 — Revalidation conditionnelle du catalogue admis

## Tranche livrée et limites

Les quatre GET existants `/v1/regions`, `/v1/species`, `/v1/cells` et
`/v1/metadata` portent désormais un `ETag` et répondent `304` quand le client
possède déjà la représentation courante validée. Aucun endpoint scientifique,
backend hébergé ou contenu public supplémentaire n'est ajouté.

**MR-022 reste IN_PROGRESS** pour la publication quotidienne de résultats admis,
le cache CDN et son invalidation d'exploitation. Les snapshots privés MR-021
ne deviennent pas publiables. L'audit scientifique reste bloquant pour les scores,
mais cette revalidation du catalogue public déjà admis est indépendante.

## Contrat HTTP

Le corps JSON réussi est sérialisé puis son SHA-256 fournit un validateur faible
`W/"<sha256>"`. Il identifie la représentation et tolère une transformation de
transport ultérieure ; ce n'est pas une signature du producteur. Chaque succès
`200` ou `304` porte `Cache-Control: private, no-cache` et le même `ETag`.
La réponse `304` n'a aucun corps ni type de contenu.

Le serveur compare faiblement les validateurs `If-None-Match`, accepte une liste
de tags forts/faibles et le joker seul. Les vérifications habituelles précèdent
la condition : disponibilité, paramètres, région et version de pagination ne
peuvent pas être contournés par un tag ou le joker. Les échecs typés
`404/409/422/503` gardent leur JSON, `Cache-Control: no-store` et aucun ETag.
Ces choix suivent [If-None-Match](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2)
et la [priorité des erreurs sur les préconditions](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.2.1).

La politique autorise un cache privé à conserver la réponse, avec revalidation
avant réutilisation ; elle n'autorise pas un cache partagé à la stocker.
Références : [private](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.7)
et [no-cache](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.4), relues
le 2 novembre 2026. Aucun TTL CDN, stale-if-error ou cache partagé n'est activé.
Cela ne transforme jamais un backend indisponible en réponse de succès.

Le parseur est borné à 4 096 caractères et 32 tags, y compris pour les en-têtes
répétés. Il respecte les virgules dans les valeurs entre guillemets. Une liste
malformée, trop longue ou hors budget est ignorée : le serveur renvoie le `200`
normal validé plutôt qu'un faux `304`. Aucun texte d'en-tête client n'est
réfléchi dans le corps ou les en-têtes de réponse.

Le tag dépend des octets sélectionnés, donc du catalogue chargé et du résultat
des filtres/pagination. Deux requêtes ayant exactement la même représentation
peuvent partager un tag. Une nouvelle version chargée ou une représentation
différente l'invalide. La disponibilité est revérifiée avant toute condition :
un catalogue devenu indisponible répond `503`, même avec un ancien tag valide.
L'erreur de version de pagination reste `409` ; le client doit relire le catalogue.

L'OpenAPI décrit l'en-tête optionnel et les réponses `200/304`. Le contrat de
corps `Page` reste inchangé. `/health`, `/ready` et les autres routes ne sont
pas couverts ; `If-Modified-Since` n'est pas implémenté dans cette tranche et
ne donne pas une priorité trompeuse à l'horloge du client.

## Fraîcheur et provenance

Le SHA et `304` ne datent ni l'acquisition des sources, ni un calcul scientifique.
Aucun `Last-Modified` n'est inventé depuis la collecte ou une date sélectionnée.
Le corps garde `published_at`, `fetched_at`, la licence, les attributions et les
dates/résolutions inconnues du catalogue admis. Une modification fictive de date
de publication du catalogue, en test uniquement, invalide son tag sans modifier
les dates source. Les éditions IGN inconnues restent inconnues.

Le catalogue reste chargé et vérifié au démarrage selon MR-009 ; les requêtes ne
surveillent pas les fichiers fournisseur ni ne lancent de job. Cette tranche
économise le transfert d'un corps déjà connu, sans prétendre supprimer la
sérialisation/validation serveur ou démontrer un gain de latence chiffré.
L'explorateur de la PR MR-044 utilise une route distincte et n'est pas modifié.
La preview Cloudflare conserve `/api/*` en `503` sans FastAPI public.

## Validation observée

34 nouveaux cas et 377 tests Python locaux réussis ; 51 PostGIS désélectionnés.
Ruff lint/format et mypy (21 sources) réussis. Un smoke contre un vrai serveur
Uvicorn local vérifie `200 → 304` sans corps et les erreurs non cachables ; le
serveur est arrêté après le contrôle. Docker Desktop est indisponible localement.
La CI construit l'image API et exécute `scripts/check_catalog_cache.py` sur l'API
réelle et le proxy web, puis PostGIS/migrations et navigateur.

Cas testés : quatre routes, filtres et pagination, invalidation de version,
backend indisponible, erreurs prioritaires, dates source conservées, horloge
cliente future, tags forts/faibles, listes/virgules/en-têtes répétés, bornes et
OpenAPI. Les tests reprennent les géométries IGN gelées déjà admises ; la seule
nouvelle date de publication est explicitement synthétique et n'est pas livrée.
Une annotation mémoire/tags et une longue description OpenAPI ont été corrigées
pendant les premiers contrôles. La CI du nouveau commit reste à observer.

Retour arrière : retirer les en-têtes/réponses conditionnelles et le smoke,
puis reconstruire l'API. Aucune migration, nouvelle ingestion, activation de
CDN, déploiement, dépense cloud ou modification de données privées.

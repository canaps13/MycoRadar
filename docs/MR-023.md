# MR-023 — Surveillance et reprise du catalogue public

## Périmètre et ordre de la roadmap

Cette tranche fournit un outil hors HTTP pour sauvegarder, vérifier, auditer et
restaurer le catalogue public MR-009 déjà admis. Les unités MR-010 à MR-015,
MR-044 à MR-046 et MR-020 à MR-022 ont leurs PR séparées ; elles ne sont pas
supposées fusionnées. Les modèles, prédictions et couches scientifiques restent
soumis aux admissions manquantes. MR-023 est la prochaine tâche indépendante
réalisable sur le socle de `main`, sans intégrer artificiellement ces PR.

**MR-023 reste IN_PROGRESS** : pas de sauvegarde PostGIS d'exploitation, de réplication hors
machine, d'alertes envoyées, de rétention automatique, de métriques des jobs ou
de supervision d'un backend public. Aucun objectif de temps ou de perte de
données de production n'est démontré. Le fichier source reste en place et aucun
service existant n'est redémarré par l'outil.

Une extension fournit un [exercice PostGIS synthétique](postgis-recovery.md) :
dump logique, corruption refusée, restauration vérifiée et conflit provoqué
pour contrôler l'annulation transactionnelle. Les résultats de cette nouvelle
révision restent à observer ; les anciens runs du catalogue ne la valident pas.

## Commandes et diagnostics

Le module `mycoradar.catalog_recovery` est inclus dans l'image API existante,
sans nouvelle dépendance ni changement de Dockerfile. Chaque commande produit
une ligne JSON : événement, opération, état, intégrité, empreinte et métriques
agrégées. Les échecs portent uniquement un code constant ; aucun chemin,
message de validation, URL fournisseur, nom de taxon ou coordonnée n'est émis.

- `backup` copie une entrée validée vers un **nouveau** fichier.
- `verify` contrôle les octets et le contrat, sans écriture.
- `restore` copie une sauvegarde validée vers un **nouveau** fichier de reprise.
- `audit` vérifie l'intégrité et applique un seuil explicite d'âge des sources.

Toutes exigent `--input` et `--sha256`. Backup/restore exigent `--output` ; audit
exige `--max-source-age-seconds` strictement positif. Codes de sortie : `0`
opération réussie, `1` échec ou arguments invalides, `2` audit valide avec alerte.
`integrity: verified` ne certifie ni fraîcheur, ni disponibilité scientifique.
Une sauvegarde ancienne peut être restaurée ; l'audit doit ensuite signaler ses
limites. Aucun résultat nouveau n'est admis par la restauration.

L'empreinte attendue doit venir de la configuration de livraison approuvée,
conservée séparément de la sauvegarde. Ne pas la recalculer depuis une sauvegarde
inconnue pour contourner une erreur : un checksum n'est pas une signature.
Le catalogue est lu une fois, au plus 32 Mio + un octet de contrôle, puis son
SHA-256 et le contrat `Snapshot` existant sont vérifiés avant toute écriture.
Visibilité publique, références, disponibilité et provenance restent contrôlées.
Les entrées non régulières et liens symboliques sont refusés. Cet outil accepte
uniquement ce contrat public, jamais une sauvegarde générique d'observations.

L'écriture crée un temporaire privé dans le répertoire cible, synchronise ses
octets puis crée un lien physique exclusif vers le nom demandé. Une destination
existante, même identique, n'est jamais remplacée ; une concurrence est refusée.
Les répertoires parents doivent déjà exister et être sous contrôle de l'opérateur.
Le système de fichiers doit autoriser les liens physiques. Le temporaire est
supprimé après l'opération. Cela évite un fichier final partiel et un écrasement ;
cela ne prouve pas la durabilité du répertoire lors d'une coupure électrique,
ni la cohérence d'un stockage réseau, ni une résistance à un acteur modifiant
simultanément les répertoires. En cas d'échec de nettoyage après publication,
la commande signale un échec : vérifier le fichier cible avant de réessayer.

## Métriques et alerte locale

Le rapport distingue l'âge de publication du catalogue, le plus ancien âge
**connu** de publication source et le plus ancien âge de collecte. Ce dernier
ne remplace jamais une date source absente. Il compte les sources sans date
de publication et conserve les états de couverture par collection.

Les codes d'alerte sont `source_date_unknown`, `sources_unavailable`,
`source_age_exceeded` et `clock_inconsistent`. Le seuil appartient à l'opérateur,
pas à une promesse de cadence fournisseur. Une date future donne un âge nul JSON
(`null`) et une alerte, jamais un âge ramené à zéro qui semblerait frais. En
présence de sources connues et inconnues, l'âge maximum connu reste disponible
avec le compteur d'inconnus et son alerte. Les métriques ne sont ni un score ni
une résolution effective ; `scientific_validation` vaut `not_performed`.

L'audit du catalogue IGN livré retourne actuellement `2` avec
`source_date_unknown` : sa date d'édition n'est pas connue. Cette alerte est
attendue et ne doit pas être masquée en remplaçant la date par la collecte.
Un ordonnanceur futur pourra surveiller la sortie et le code ; aucun message
n'est transmis à un tiers et aucun ordonnanceur n'est activé ici.

## Runbook de reprise locale

Exemple PowerShell depuis la racine avec l'environnement Python installé.
Les répertoires sont locaux et ignorés par Git. Le SHA par défaut vient du reçu
versionné de la publication déjà admise ; pour une livraison externe, utiliser
son empreinte approuvée indépendamment.

```powershell
$env:PYTHONPATH = 'api/src'
$catalogueSha = (Get-Content api/src/mycoradar/data/public-catalog.sha256).Trim()
New-Item -ItemType Directory -Force .tools/catalogue-recovery | Out-Null
uv run --locked python -m mycoradar.catalog_recovery backup --input api/src/mycoradar/data/public-catalog.json --sha256 $catalogueSha --output .tools/catalogue-recovery/backup-001.json
uv run --locked python -m mycoradar.catalog_recovery verify --input .tools/catalogue-recovery/backup-001.json --sha256 $catalogueSha
uv run --locked python -m mycoradar.catalog_recovery restore --input .tools/catalogue-recovery/backup-001.json --sha256 $catalogueSha --output .tools/catalogue-recovery/restored-001.json
uv run --locked python -m mycoradar.catalog_recovery audit --input .tools/catalogue-recovery/restored-001.json --sha256 $catalogueSha --max-source-age-seconds 86400
```

Contrôler chaque code de sortie avant la commande suivante. Un refus de checksum
ou de contrat impose de choisir une autre sauvegarde approuvée ; ne pas éditer
ses métadonnées pour la rendre valide. Si le nom cible existe, vérifier ce fichier
et choisir un autre nom. La copie locale n'est pas une protection contre la perte
du disque : le stockage de sauvegarde externe et ses droits restent à définir.

Pour une instance **locale** de récupération, dans un nouveau processus :

```powershell
$env:MYCORADAR_CATALOG_PATH = (Resolve-Path .tools/catalogue-recovery/restored-001.json).Path
$env:MYCORADAR_CATALOG_SHA256 = $catalogueSha
uv run --locked uvicorn mycoradar.main:app --host 127.0.0.1 --port 18001
```

Vérifier `/v1/regions?limit=1&country=FR` : version égale au SHA approuvé,
géométrie et provenance identiques. `/v1/species` reste `unavailable` dans la
publication actuelle. `/health` seul ne suffit pas ; `/ready` contrôle PostGIS,
qui n'est pas sauvegardé par cet outil de catalogue. Si l'instance de reprise échoue, l'instance
précédente et sa configuration sont conservées. L'activation sur un hébergement
public ou le redémarrage d'un service de production demandent leur autorisation
spécifique ; ils ne sont pas exécutés par cette tranche.

## Exercice automatisé et limites de validation

`scripts/check_catalog_recovery.py` lance les vraies commandes dans des processus
séparés : sauvegarde, vérification, corruption injectée refusée, restauration
exacte, nouvelle corruption refusée et audit des dates inconnues. Il démarre
ensuite un vrai serveur Uvicorn temporaire, contrôle les régions restaurées et
l'indisponibilité des espèces, puis l'arrête. Aucune copie n'est publiée.

La CI exécute ce script dans l'image finale API, sous son utilisateur non root,
sans réseau externe (`--network none`) et avec les seuls scripts montés en lecture
seule. Les fichiers d'exercice sont temporaires. Les tests couvrent aussi les
échecs fsync/lien, un écrivain concurrent, les bornes de lecture, le refus de
données privées, la non-divulgation des diagnostics et les changements d'horloge.
Les résultats locaux et CI sont consignés dans la PR ; tant qu'ils ne sont pas
observés, ils ne constituent pas une preuve. L'exercice PostGIS distinct ne
certifie aucune sauvegarde de données réelles, panne électrique ou reprise hors machine.

Validation locale : 26 nouveaux cas de reprise et 369 tests Python réussis
(51 PostGIS désélectionnés), Ruff lint/format, mypy sur 21 sources et
`git diff --check` réussis. L'exercice CLI et HTTP Uvicorn réel réussit sur
Windows. Docker Desktop ne répond pas (pipe LinuxEngine absent) ; l'exécution
de l'image finale reste à observer en CI, sans la remplacer par le smoke natif.

Retour arrière : retirer l'outil et le smoke, reconstruire l'image API ; aucune
migration et aucun fichier de catalogue existant ne sont modifiés.

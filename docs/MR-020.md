## Runner local — extension du 2 novembre 2026

```powershell
$env:PYTHONPATH='api/src'
uv run --locked python -m mycoradar.queue_runner --config data/queue-runner/synthetic/runner.json --state .tools/runner-private --once
# Mode de service explicite, au premier plan ; Ctrl+C pour arrêter :
uv run --locked python -m mycoradar.queue_runner --config data/queue-runner/synthetic/runner.json --state .tools/runner-private --serve
```

Cette recette utilise un fixture **inventé**. Un producteur réel doit déposer
ses artefacts JSON autonomes privés dans `racine/versions/<sha256>.json`, puis
remplacer atomiquement `racine/current.json` par `{"sha256":"<empreinte>"}`.
La racine est configurée relativement au fichier de configuration. L'adaptateur
`verified-json-v1` lit uniquement le petit pointeur lors du polling, puis vérifie
les octets et la structure JSON lors du traitement. Il ne calcule aucun score,
n'interprète pas scientifiquement le payload et ne renouvelle pas ses sources.

Configuration : `schema_version=queue-runner-v1`, une à seize sources, chacune
avec `id`, `root`, `pipeline_version`, `adapter` et `interval_s` optionnels.
L'adaptateur seul autorisé est `verified-json-v1` ; aucun chemin de programme,
import arbitraire, commande ou endpoint réseau n'est accepté. Un état doit
rester sur stockage local persistant, hors Git et hors répertoire web servi.
La configuration opérateur vaut au plus 64 Kio, les pointeurs 256 octets et
chaque payload 8 Mio ; JSON avec clés répétées, constantes non finies ou objet
racine incorrect refusé. Les chemins résolus restent sous leurs racines.

Le cache privé de configurations conserve chaque ancienne configuration sous
son empreinte. Un changement de pipeline ou de racine n'envoie pas les anciens
jobs vers la nouvelle entrée : ils retrouvent leur configuration et leur version
exactes. Les producteurs doivent conserver les versions encore nécessaires à
la file. Retirer une source de la configuration arrête son polling mais ne
supprime pas ses jobs déjà en attente. Un arrêt complet se fait en arrêtant
le runner ; aucune purge automatique n'est ajoutée.

Les copies vérifiées vont sous `state/objects/`, les reçus stables sous
`state/receipts/`. Une reprise identique conserve octets et mtime ; un conflit
refuse l'écrasement. Chaque reçu garde `publication_allowed=false` et
`scientific_validation=not_performed`. Aucune route HTTP ne sert ces fichiers.
Le pointeur n'est pas une signature du producteur, ni une admission de droits :
la revue de provenance, de rétention et d'accès reste requise pour de vrais lots.

`--once` effectue un tour, avec au plus seize jobs par défaut (1–100 configurables).
`--serve` vérifie les échéances toutes les trente secondes par défaut (5–60),
sans rappeler les producteurs avant leur échéance de polling/cooldown. Le mode
de service ne démarre qu'à cette commande explicite. SIGINT/SIGTERM demandent
l'arrêt ; les jobs et les états persistants restent reprenables. Les résumés
stdout ne contiennent que des compteurs et états, sans ID, chemin ou payload.
Une panne, un arrêt de source ou un job `dead` produit un état `degraded` ;
une entrée globale invalide produit un diagnostic fixe et le code 2.

Treize nouveaux tests couvrent le vrai runner, la CLI, les redémarrages,
versions/configurations anciennes, budgets, refus de corruption, chemins résolus
sortants simulés et arrêt explicite. Le smoke lance deux processus CLI successifs
sur l'entrée en lecture seule : une seule ingestion. Le Dockerfile API existant
copie ces modules standard/Pydantic sans ajouter de dépendance ou lancer le
service ; la CI rejoue le smoke avec `--network none`. Pas de branchement aux
adaptateurs distants des autres PR ni de mise en service implicite.

## Contrat utilisable

```python
from pathlib import Path
from mycoradar.job_queue import JobQueue

queue = JobQueue(Path(".tools/operator-queue.sqlite"))
queue.register("provider-quota-group", "ingestion-v1")
# Le runner fournit les adaptateurs revus, hors requêtes HTTP :
# queue.poll("provider-quota-group", probe_reviewed_source_version)
# queue.run_one(ingest_idempotently)
print(queue.counts())
```

`probe` retourne une empreinte SHA-256 de version admise, ou `None` pour
« inchangée » après une première version connue. Il doit respecter les règles
d'accès, de cache et les délais réseau du produit. Le code vérifie le format
de l'empreinte, pas son authenticité ni l'admission des droits. Une empreinte
ne remplace pas le manifeste de provenance du lecteur.

`register` crée un groupe de quota et sa version de pipeline, sans exécuter
de probe. Les IDs sont bornés à 80 caractères. Un même quota fournisseur doit
partager un seul groupe, pas plusieurs alias. La cadence normale est d'au moins
3 600 secondes et d'au plus sept jours, calculée après la fin du dernier
contrôle réussi. Cela définit une échéance, pas une garantie de déclenchement :
le futur runner doit être appelé et surveillé. Une modification de pipeline
respecte l'échéance et le cooldown existants ; une configuration en cours de
probe ne peut pas être changée. La même configuration est un no-op.

`poll` prend un bail persistant puis appelle le probe hors transaction. Une
version déjà vue ne crée pas de doublon. La clé est le SHA-256 de
`[groupe, version_pipeline, version_source]` : changer explicitement le pipeline
peut demander un nouveau traitement de la même source. Les entrées terminées
restent conservées pour la déduplication ; aucun nettoyage automatique n'en
efface la mémoire. Un résultat de probe tardif dont le bail a expiré est refusé.

`RetryLater(secondes)` représente un délai fournisseur déjà interprété par
l'adaptateur (par exemple HTTP 429). Le socle n'interprète pas HTTP ni ses dates.
Timeout/OSError ou version invalide donnent un backoff exponentiel de 60 s
jusqu'à une heure. Le délai effectif n'est jamais inférieur au délai fournisseur.
Ce cooldown bloque les prochains probes et acquisitions de jobs du même groupe,
sans annuler un appel déjà commencé. Même un délai explicite reçu après
expiration d’un bail reste appliqué, sans autoriser la publication tardive
de sa version ni son acquittement. Les groupes indépendants restent utilisables.
Le nombre d'appels internes d'un adaptateur reste sous sa propre gestion de quotas.
Il n'y a aucune boucle de retry immédiate dans le socle.

Un délai fournisseur négatif, non entier ou supérieur aux sept jours supportés
**arrête le groupe** plutôt que de le raccourcir. `resume(groupe)` est une action
opérateur après revue ; elle ne supprime jamais un cooldown valide encore actif.
Un job ayant rencontré ce délai invalide est conservé en échec définitif.

## Baux, exécution et écritures idempotentes

`claim` acquiert au plus un job prêt, de façon transactionnelle. Un seul worker
gagne la même acquisition, même dans deux processus. Le bail vaut 300 secondes
par défaut, configurable entre 1 et 3 600 ; `renew(job)` le prolonge tant que
son jeton est actif. Les probes doivent finir avant leur bail ; les jobs longs
doivent renouveler leur bail avec un runner adapté. Ce socle ne lance pas de
thread de heartbeat caché.

`run_one` invoque l'adaptateur hors transaction et l'acquitte après succès.
Les erreurs temporaires donnent une nouvelle échéance persistante, avec trois
essais maximum par défaut (configurable entre 1 et 10). L'épuisement, y compris
après des crashes au dernier essai, laisse le job `dead`, sans retry automatique.
Une erreur inattendue peut interrompre le runner : son bail expire puis permet
la reprise, sous le même budget. Aucun corps d'erreur n'est écrit en base.

`finish` et `renew` refusent un jeton expiré, remplacé ou déjà acquitté. Le fencing
de la file n'est pas une transaction distribuée avec la destination : une panne
après écriture et avant acquittement peut réexécuter l'adaptateur. Celui-ci doit
utiliser `Job.id` comme clé unique ou clé d'idempotence dans sa transaction de
destination, avec contrôle de version adapté. Le test de coupure après commit
exécute deux fois le handler et conserve une seule écriture de destination.
Le socle ne revendique pas une exécution exactement une fois.

## Persistance et limites

Schéma SQLite de contrôle `user_version=1`, créé uniquement dans un fichier
opérateur explicite. Une autre base ou révision inconnue est refusée ; aucun
reset ou changement de schéma implicite. Les configurations de bail, budget
d'essais et capacité doivent être identiques entre workers du même fichier.
Un recul de l'horloge au-dessous du dernier instant enregistré bloque l'opération
plutôt que de publier une chronologie inventée. Les instants sont des secondes
UTC de contrôle, distinctes des dates et de la fraîcheur scientifiques.

Au plus 100 groupes et 10 000 jobs, capacité configurable à la baisse. La
saturation refuse un nouveau job sans avancer le watermark ni oublier les
clés précédentes. La rétention/rotation devra conserver la déduplication avant
tout agrandissement ou purge. Aucun payload d'occurrence, URL, secret, exception
ou donnée raster n'est stocké ; les IDs et SHA restent néanmoins à protéger.
Le fichier doit rester hors Git, avec contrôle d'accès et stockage local durable
sur un seul hôte. Un `/tmp` de conteneur ne constitue pas une persistance
d'exploitation. La coordination multi-hôte, la sauvegarde et la supervision
restent des travaux distincts (MR-023 notamment).

## Validation

```powershell
$env:PYTHONPATH='api/src'
uv run --locked python scripts/check_job_queue.py
```

Le smoke utilise uniquement une base temporaire et des sources inventées. Il
lance deux processus concurrents : un seul acquiert le job. Il reprend le bail,
vérifie la déduplication d'une version inchangée, une nouvelle version, le délai
fournisseur, puis une panne temporaire suivie d'une reprise. Résultat : deux
jobs terminés, zéro source réelle appelée. La CI exécute exactement ce smoke
dans l'image API construite, `--network none`, script monté en lecture seule.
Le Dockerfile reste inchangé : bibliothèques standard, Uvicorn et UID 10001.

Les 32 tests ciblés réussissent localement : cadence/rejeu/redémarrage,
concurrence, expiration/heartbeat/fencing, 429, délai invalide sans retry trop
tôt, backoff global, coupure après commit, budgets, base étrangère et horloge.
La suite complète réussit : 375 Python, 51 PostGIS désélectionnés, Ruff
lint/format et mypy (21 sources). Le [reçu local](evidence/MR-020-local.json)
conserve moteur, empreintes et sortie du smoke ; la CI reste à observer.
Docker local est indisponible (pipe Docker Desktop absent) ; son exécution
est confiée au workflow Compose. Les premières vérifications Ruff ont signalé
des lignes SQL trop longues, corrigées avant la validation.

Retour arrière : retirer module, smoke et recette CI, puis reconstruire l'API.
Conserver la base opérateur pour sa mémoire de déduplication tant qu'une reprise
est prévue. Aucun changement de schéma PostGIS, fichier métier, provider réel,
Worker Cloudflare, secret, dépense cloud, fusion ou déploiement.
